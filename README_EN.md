Sebastian is an LLM-powered multi-agent terminal assistant: a central Brain Agent orchestrates specialized sub-agents that execute code in an isolated sandbox, manipulate files, and search the web, backed by long-term memory across sessions. The project originated from a university course design and encompasses architecture design, security defense, and engineering implementation.

## Design Philosophy

Every design decision in Sebastian corresponds to an explicit design principle. Understanding these principles means understanding the design of the entire system.

### 1. Declarative Design — Capability Is a File

**Principle**: Extending system capabilities should not require modifying core code.

**Implementation**: Sub-agents and skills are defined as plain Markdown files (`YAML frontmatter` + body) placed in convention directories, discovered and registered automatically at startup:

- Add a sub-agent → place a `.md` definition file in `src/agents/subagents/` (or the user directory `~/.sebastian/.agents/`)
- Add a skill → place a definition file at `~/.sebastian/skills/<name>/SKILL.md`

No code changes required; effective upon restart. Extensibility is guaranteed by filesystem conventions (Convention over Configuration), rather than config formats or plugin APIs.

### 2. Separation of Command and Execution — The Brain Agent Does Not Execute Tasks

**Principle**: An agent serving as both commander and executor will find its context size hard to control.

**Implementation**: The Brain Agent is responsible only for intent parsing and task triage — understanding user intent, planning tasks, dispatching sub-agents, and summarizing results. The four sub-agents (CodeWriter / CodeReviewer / TestRunner / WebSearchAgent) each maintain an isolated LLM context, a dedicated toolset, and their own system prompt, and are destroyed upon task completion. Single responsibility, focused prompts, undisturbed context.

### 3. Never Trust the LLM — Model Output Must Pass Security Checks First

**Principle**: LLM output is untrusted generated content; any command, path, or URL it produces could be induced into an attack payload.

**Implementation**: Every command generated by the LLM must pass four layers of defense-in-depth validation before execution:

```
LLM output → [Command Guard] blocks 21 dangerous patterns: rm -rf /, fork bombs, raw device writes...
           → [Path Guard] absolute paths only + $HOME boundary + sensitive directory blacklist
           → [URL Guard] blocks private/loopback/multicast addresses — SSRF protection
User input → [Input Guard] blocks prompt injection / jailbreak attempts
```

Bypassing any single layer never compromises the whole defense — the value of defense in depth lies in eliminating single points of failure.

### 4. Isolation over Trust — Security Through Boundaries

**Principle**: Rather than relying on assumptions about code behavior, constrain its capabilities at the mechanism level.

**Implementation**: Isolation is enforced at three levels:

| Isolation Level | Mechanism | What It Isolates |
|-----------------|-----------|------------------|
| Process-level | Code executes in a bubblewrap namespace sandbox | Host filesystem (read-only mount), 38 sensitive directories (tmpfs-hidden), system capabilities (`cap-drop ALL`) |
| Process-level | Approval dialogs run as independent Python subprocesses | Tcl/Tk thread-safety — each dialog owns its event loop; safe from any thread |
| Context-level | Sub-agents keep isolated contexts, destroyed after each task | Cross-agent conversation pollution and nested dispatch |

### 5. Graceful Degradation — Faults Are Tolerated, Recovery Is Required

**Principle**: LLM context windows are finite, API services may be unstable, and models may return empty responses — failure is the norm rather than the exception.

**Implementation**: Three tiers of fault tolerance work in combination:

- **4-layer context compaction pipeline**: persist large results → snip messages → micro-compact → LLM summarization; the context never overflows
- **Reactive compaction**: on `context_length_exceeded` errors, compact immediately and retry (up to 3 times) — conversations never break
- **Exponential backoff retries**: API failures retry up to 5 times; empty responses from reasoning models are logged and handled gracefully instead of failing silently

### 6. Human-Machine Collaboration — Machines Request, Humans Decide

**Principle**: Automation does not mean removing humans from the loop. The final decision on irreversible operations always remains with the user.

**Implementation**: Before dangerous operations (bash / write / edit / agent dispatch) are executed, the system raises a dedicated always-on-top confirmation dialog showing the full tool parameters (syntax-highlighted), with keyboard shortcuts and timeout auto-deny. Meanwhile, the memory system enables Sebastian to record user preferences and constraints across sessions — all memory content originates from the user's explicit statements in conversation.

## Architecture Overview

```
┌──────────────────────────────────────────────────────────────────┐
│                        CLI (Typer)                                │
│    UserPromptSubmit Hook → input security check → Brain Agent    │
└─────────────────────────────┬────────────────────────────────────┘
                              │ streaming output + memory injection
         ┌────────────────────▼─────────────────────┐
         │              Brain Agent                  │
         │  · Intent parsing and task triage         │
         │  · Task planning (Todo Manager)           │
         │  · Memory system (select/extract/merge)   │
         │  · Skill loading (Skill Registry)         │
         │  · Sub-agent dispatch (async-capable)     │
         └──┬──────────┬──────────┬──────────┬──────┘
            │          │          │          │
    ┌───────▼──┐ ┌─────▼────┐ ┌──▼────┐ ┌──▼────────┐
    │CodeWriter│ │CodeReview│ │TestRnr│ │WebSearchAg│
    │ 6 tools  │ │ 4 tools  │ │5 tools│ │  2 tools  │
    └──────────┘ └──────────┘ └───────┘ └───────────┘

    Every tool call passes through the Hook pipeline:
    PreToolUse → [logging] → [HITL confirmation dialog]
    Execution passes through the security pipeline:
    command guard → path guard → URL guard → bubblewrap sandbox
```

The **Brain Agent** is the only top-level agent interacting with the user. Its system prompt includes: path-safety baselines, Bash usage conventions, a task-dispatch strategy table, task planning instructions, available skills and sub-agents, background execution rules, and a dynamically injected memory index.

## Core Features

### Multi-Agent Collaboration

The Brain Agent routes subtasks to specialized sub-agents via the `agent` tool; sub-agents are destroyed after completion and return only their final result for natural-language summarization. Sub-agent definitions are plain Markdown (`YAML frontmatter` + body), with user-level overrides supported.

| Sub-Agent | Tools | Role |
|-----------|-------|------|
| **CodeWriter** | read, ls, glob, write, edit, grep | Read and understand existing code, generate new code |
| **CodeReviewer** | read, ls, glob, grep | Review code quality, style, and potential issues |
| **TestRunner** | read, ls, bash, grep, glob | Run tests and report results (never edits test code) |
| **WebSearchAgent** | web_search, web_fetch | Web search and page content extraction |

### Tool System

All tools are registered in a central `ToolsRegistry`; each tool carries four attributes: name, implementation, JSON Schema, and HITL flag. Tools are allocated per agent — the Brain Agent has access to all 12, while sub-agents receive their toolsets through dynamic registration at runtime (sub-agents are never allowed to dispatch other sub-agents).

| Tool | HITL | Description |
|------|:----:|-------------|
| `bash` | ✓ | Execute shell commands in the bubblewrap sandbox (async-capable) |
| `read` | | Read files (full or offset+limit slices) |
| `write` | ✓ | Overwrite files (PDF/DOCX blocked) |
| `edit` | ✓ | Exact find-and-replace (supports replaceAll) |
| `ls` | | List directory contents |
| `glob` | | Pattern-based file matching |
| `grep` | | Regex content search |
| `web_search` | | DuckDuckGo search (timeout-protected) |
| `web_fetch` | | Web page extraction (SSRF pre-checked) |
| `todo` | | Task planning with progress visualization |
| `load_skill` | | Load a skill document |
| `agent` | ✓ | Dispatch a sub-agent (async-capable) |

### Memory System

Sebastian maintains long-term memory across sessions in `~/.sebastian/.memory/`, driven by three LLM pipelines:

| Pipeline | Trigger | Purpose |
|----------|---------|---------|
| **Select** | Start of every turn | Retrieve memories relevant to the current question and inject them into context |
| **Extract** | End of every turn | Extract user preferences, constraints, and project facts into memory files |
| **Consolidate** | Memory files ≥ 10 | Merge duplicates, remove stale entries, cap the total |

The memory index is dynamically appended to the system prompt (refreshed on every AgentLoop entry), and memory content is injected into the user message via `<relevant_memories>` tags. Memory-related API calls automatically disable reasoning-model thinking (`thinking: disabled`) with backend fallback, so reasoning never consumes the output budget.

### Security System

Four layers of defense in depth plus one human confirmation layer:

| Layer | Module | Responsibility |
|-------|--------|----------------|
| Input | `input_guard.py` | Prompt injection / jailbreak detection (Chinese + English patterns) |
| Command | `command_guard.py` | Blocks 21 dangerous patterns: `rm -rf /`, fork bombs, raw `dd` device writes, etc. |
| Path | `path_safety.py` | Absolute paths + `$HOME` boundary + sensitive dir/file/extension blacklists + symlink resolution |
| Network | `url_safety.py` | SSRF protection (private ranges, loopback, link-local, multicast, IPv6 ULA) |
| Confirmation | HITL dialog | Destructive operations require explicit human approval |

### Human-in-the-Loop Approval

HITL uses the subprocess dialog approach (`approval_client.py` + `approval_dialog.py`):

- Each approval spawns an independent Python process running a tkinter dialog — thread-safe, no risk from any agent thread
- The parameter card displays the full tool arguments with syntax highlighting (strings/numbers/booleans colorized)
- Keyboard shortcuts (Y/Enter to allow, N/Esc to deny) and countdown timeout with auto-deny
- Three built-in themes: dark / light / blue

### Sandbox

Code execution is isolated with **bubblewrap** using Linux namespaces:

- Namespaces: PID, IPC, UTS, cgroup isolation; `--cap-drop ALL` drops every capability
- Host filesystem mounted read-only, `~` writable; **38 sensitive directories** (`.ssh`, `.aws`, browser profiles, credential stores, shell histories, etc.) are tmpfs-hidden
- **21 config files** (`.bashrc`, `.gitconfig`, language toolchains, etc.) mounted read-only
- 180-second execution timeout; the sandbox lifecycle is bound to the parent process and terminates with it

### Hook System

An event-driven plugin mechanism injects custom logic at four points of the agent lifecycle:

| Event | Trigger Point | Registered Hooks |
|-------|---------------|------------------|
| **UserPromptSubmit** | After user input | Input security check |
| **PreToolUse** | Before tool execution | Call logging + HITL confirmation dialog |
| **PostCompletion** | After each LLM response | Token usage accumulation |
| **Stop** | After each conversation turn | Per-turn token summary |

### Context Compaction

**Automatically triggered every 5 AgentLoop turns**, the four-layer progressive compaction pipeline:

1. **Persist large results**: tool results over 50KB are written to disk, only a preview remains in context
2. **Snip messages**: keep the first 3 + last 47 messages when exceeding 50
3. **Micro-compact**: old tool results are replaced with placeholders
4. **LLM summarization**: over 500K characters, the conversation is summarized via API (the original is archived as a transcript)

Context overflow additionally triggers **reactive compaction** (up to 3 retries); `/compact` triggers it manually.

### Background Tasks

The `bash` and `agent` tools support `run_in_background=true` for async execution: tasks run in daemon threads and proactively notify the Brain Agent via `<task_notification>` upon completion. The Brain's system prompt encodes the scheduling rules: parallelizable tasks are not executed serially, and async tasks do not block the main flow.

### Session Management

- Sessions are saved as JSONL files: `~/.sebastian/session/{session_id}.jsonl`
- Auto-saved on exit; restored via `sebastian -s <SESSION_ID>`; the 10 most recent sessions are retained
- In-chat: `/clear` wipes history, `/compact` compacts manually

### Skill System

Skill documents live in `~/.sebastian/skills/<name>/SKILL.md` (YAML frontmatter + Markdown body), loaded on demand by the Brain Agent through the `load_skill` tool. Skills are fully pluggable — adding or removing files requires no code changes. Deployed example skills include: nmap, theHarvester, tcpdump, tshark, traceroute, whois, SSL certificate checking, subdomain enumeration, and more.

## Quick Start

### Requirements

- **OS**: Linux (the bubblewrap sandbox relies on Linux namespaces)
- **Python**: >= 3.10
- **bubblewrap**: `sudo apt install bubblewrap`
- **python3-tk**: `sudo apt install python3-tk` (required by the HITL confirmation dialog)
- **Network**: access to the DeepSeek API (or any OpenAI-compatible backend)

### Installation

```bash
# 1. Clone the repository
git clone <your-repo-url> Sebastian
cd Sebastian

# 2. Install (recommended — registers the sebastian command)
pip install -e .

# or install from requirements.txt
pip install -r requirements.txt

# 3. Install system dependencies (Ubuntu/Debian)
sudo apt install bubblewrap python3-tk
```

### Configure the API Key

```bash
# Interactive setup wizard (the API key input masks everything except the prefix)
sebastian setup
```

Configuration is written to `.env` in the project root:

```bash
DEEPSEEK_MODEL=deepseek-v4-flash
DEEPSEEK_API_KEY=sk-your-key
DEEPSEEK_BASE_URL=https://api.deepseek.com
```

Any OpenAI-API-compatible service is supported (OpenAI, DeepSeek, Ollama, vLLM, etc.).

### Run

```bash
sebastian
```

## CLI Commands

### Startup

```bash
sebastian                       # standard start (new session)
sebastian -v / --version        # show version
sebastian -s <SESSION_ID>       # restore a session
sebastian --session <SESSION_ID>
sebastian setup                 # API configuration wizard (masked key input)
```

### In-Chat Commands

| Command | Description |
|---------|-------------|
| `quit` / `/quit` / `/exit` | Save session and exit |
| `/clear` | Clear the current conversation history |
| `/compact` | Manually trigger LLM summarization compaction |
| `Ctrl+C` / `Ctrl+D` | Exit without saving |
